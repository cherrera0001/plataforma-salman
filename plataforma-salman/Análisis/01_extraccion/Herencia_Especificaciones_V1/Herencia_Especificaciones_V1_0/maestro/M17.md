# M17. Arquitectura y contratos de integración

Versión 1.0 | 25 de octubre de 2026 | Especificación propuesta para revisión


## Solución técnica propuesta
Se propone un monolito modular TypeScript con web y API en Next.js 16, runtime Node.js 24 LTS y PostgreSQL 17. Un worker del mismo repositorio ejecuta outbox, importaciones y notificaciones. Las familias de versiones se contrastaron con fuentes oficiales [S02/S03/S08]; los parches exactos, dependencias y licencias deben fijarse y revisarse en F00. Es una propuesta ADR pendiente de ratificacion, no una selección atribuida al equipo.
El dominio no depende de Next ni del proveedor de IA. Web/API y worker comparten librerias de reglas y repositorios transaccionales. Un sólo almacen relacional es autoridad operativa; objetos/documentos van a almacenamiento privado con enlaces temporales. No se requieren microservicios ni Redis para el volumen inicial. Los adaptadores de pago, canal, mensajeria, DTE y bancos quedan reemplazables.
## API propia y eventos
El contrato OpenAPI 3.1 describe recursos internos, solicitudes, respuestas, errores y seguridad. No afirma que las rutas propias existan en Meta o Booking. Escrituras sensibles exigen Idempotency-Key, control de versión y permiso; mismo key con payload distinto devuelve conflicto. Errores tienen código estable, correlation_id y campos invalidos sin datos privados. Listas usan cursor y límites; exportaciones voluminosas son trabajos autorizados.
Eventos de dominio tienen event_id, versión, sociedad/unidad, aggregate_id, occurred_at, correlation_id y payload mínimo. Entrega es al menos una vez; consumidores deduplican. No se promete exactly-once entre proveedores. Reintentos exponenciales con límite y cola de fallas; un timeout de pago desconocido exige consulta, no repetir cargo.
## Integraciones externas
Cada capacidad registra proveedor/cuenta, auth, permisos, versión API, límites, webhooks, costo, privacidad, exportación y revocacion. Sus estados van de DOCUMENTADA a PRODUCCION_VERIFICADA por evidencia, no por instalar un SDK. Webpay se válida segun su flujo; Instagram y WhatsApp conservan restricciones propias; Booking requiere canal autorizado. Bancos empiezan por importación y luego lectura consentida.
## Disponibilidad y cambio
Precio, cupo, pago, cuenta y tarea tienen una sola autoridad declarada. Los cambios de contrato tienen versión y compatibilidad; un cambio que rompe consumidores requiere migración coordinada. Los mocks se identifican como tales y nunca activan una capacidad productiva. Ver contratos/openapi.yaml, eventos.json y adaptadores.md. Los planes técnicos por funcionalidad son PRELIMINARES hasta ratificar stack, proveedores y recursos.
