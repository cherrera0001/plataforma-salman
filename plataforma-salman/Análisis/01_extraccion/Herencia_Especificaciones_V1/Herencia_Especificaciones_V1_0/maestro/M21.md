# M21. Pruebas, cobertura y aceptacion

Versión 1.0 | 25 de octubre de 2026 | Especificación propuesta para revisión


## Unidad de comprobacion
Cada requisito conserva su ID de origen y se vincula a FR local, historia, regla, dato, pantalla o servicio, contrato, tarea, prueba y evidencia. Los 153 requisitos no se usan como techo: cualquier necesidad nueva exige ID y control de cambios. Los 18 controles SDD son gobierno del proceso y no se suman como funcionalidades hoteleras para inflar avance.
Se entregan criterios y casos, no resultados de software. Todas las pruebas hoteleras parten NO_EJECUTADA. El validador documental sólo comprueba consistencia estructural, referencias, conservación de baseline y ciertas invariantes de datos_sinteticos/fixture.json; no prueba reservas reales ni integraciones.
## Estrategia
Unitarias: importes exactos, fechas, políticas, capacidad, reparto y estados. Integración: transacciones, constraints, aislamiento y persistencia real. Contrato: esquemas, errores, firma y reintento de adaptadores. Extremo a extremo: venta desde enlace o conversacion hasta banco. Seguridad: acceso indebido, precio manipulado, secretos y tokens. Recuperación: restauración, cola pendiente y conciliación con hechos externos.
Datos de prueba son ficticios identificados. Para último cupo se lanzan solicitudes simultaneas y se verifica una sola asignación interna. Repetir diez veces una notificación no genera diez cobros. Dos movimientos bancarios legitimos iguales permanecen separados. Un desayuno producido y luego servido no consume dos veces los ingredientes. El acta de traspaso debe cuadrar contra la importación.
## Umbrales y evidencia
Aceptacion propuesta: todos los P0 del alcance activo superados, cero defectos críticos abiertos, controles financieros exactos por moneda y ausencia de fuga entre sociedades. Rendimiento se mide con carga declarada, no en una única consulta. Cobertura de lineas no sustituye cobertura de requisitos. Toda desviacion P1 requiere decisión y fecha; no basta porcentaje global alto.
La evidencia incluye caso, datos anonimizados, build, entorno, pasos, esperado, observado, logs seguros y revisor. Una captura de pantalla sola no prueba persistencia o concurrencia. Checklists custom las marca el revisor, no quien quiere avanzar.
